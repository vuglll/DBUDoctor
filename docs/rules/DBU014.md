# DBU014: Serving endpoint without scale-to-zero

Severity: warning in a target with `mode: development`, info elsewhere. Introduced in 0.7.

A model serving endpoint's served entity does not set `scale_to_zero_enabled: true`.

## Why it matters

With scale to zero, an endpoint scales "down to zero after 30 minutes of inactivity". Without it, the endpoint keeps its provisioned concurrency running when no requests come in ([custom model serving](https://docs.databricks.com/aws/en/machine-learning/model-serving/custom-models), checked 2026-11-09). The floor is `min_provisioned_concurrency`, or the lower bound of the `workload_size`: Small 4, Medium 8, Large 16 ([Serving endpoints API](https://docs.databricks.com/api/workspace/servingendpoints/create)). The message names it.

Development endpoints sit idle most of the time, so an always-on one there is a warning. In production, Databricks says scale to zero "should not be used for production workloads that require consistent uptime or guaranteed response times", so DBU014 only reports info there.

DBUDoctor does not price serving endpoints.

## Example

```yaml
targets:
  dev:
    mode: development
resources:
  model_serving_endpoints:
    scoring:
      config:
        served_entities:
          - entity_name: main.ml.churn
            entity_version: "3"
            workload_size: Small
            scale_to_zero_enabled: false   # DBU014 (warning in dev)
```

## How to fix

```yaml
            scale_to_zero_enabled: true
```

The first request after the endpoint scales to zero waits for a cold start, usually 10 to 20 seconds. For production endpoints that must stay warm, lower `min_provisioned_concurrency` or the `workload_size` instead.

## When to suppress

Suppress when the endpoint serves traffic that needs guaranteed response times:

```yaml
suppressions:
  - rule: DBU014
    resource: model_serving_endpoints.fraud_scoring
    reason: Checkout fraud scoring needs < 200 ms p99 (RISK-4)
```
