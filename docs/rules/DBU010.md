# DBU010: Sharp frequency increase

Severity: warning. Introduced in 0.1.

A job runs at least `factor` times (default 4) as often as in the base branch, and at least `min_runs` (default 100) more times a month.

## Why it matters

A one-line cron change multiplies cost: every run pays for compute, and a classic job cluster also pays for startup time, which Azure bills from the VM's Starting phase. Moving from hourly to every 15 minutes is 730 → 2,920 runs a month, four times the cost at the same run duration.

Runs per month are the fire times in the 365 days after 1 January of the current year, divided by 12, evaluated in the job's `timezone_id`. Event-driven jobs (file arrival, table update) have no known frequency and are not checked.

## Example

```yaml
resources:
  jobs:
    orders_sync:
      schedule:
        quartz_cron_expression: "0 0/15 * * * ?"   # was "0 0 * * * ?"; DBU010
        timezone_id: UTC
```

## How to fix

Check that the new schedule matches how fresh the data must be, and keep the old cadence if it is enough. If frequent runs are needed, move them to compute that starts quickly (serverless or an instance pool), so each run does not pay for a cluster start.

## When to suppress

Suppress when the higher frequency is a deliberate requirement and its cost has been approved. Tune the thresholds instead when the defaults are too sensitive for the repository:

```yaml
rules:
  DBU010: { factor: 6, min_runs: 500 }
suppressions:
  - rule: DBU010
    resource: jobs.orders_sync
    reason: Orders dashboard SLA moved to 15 minutes (PRODUCT-77)
```
