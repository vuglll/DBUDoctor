# DBU007: Job without a timeout

Severity: info. Introduced in 0.5.

A job has no `timeout_seconds` (absent or 0), and at least one of its tasks has none either. Continuous jobs are skipped; [DBU005](DBU005.md) covers them.

## Why it matters

"A value of `0` means no timeout", and 0 is the default for both the job and its tasks ([Jobs API](https://docs.databricks.com/api/workspace/jobs/create), checked 2026-11-09). Without a timeout, a run that hangs (a stuck stream, a deadlocked driver, a query waiting on a lock) keeps its compute busy until someone cancels it.

On classic compute that is the cluster's full rate: a job cluster with a driver and 4 workers of `Standard_DS3_v2` on Azure bills about $2.27 an hour, so a run stuck over a weekend costs about $150. The message gives the job's rate when the catalog knows it.

`health` rules on `RUN_DURATION_SECONDS` send notifications but do not stop the run, so they do not count as a timeout.

## Example

```yaml
resources:
  jobs:
    nightly_etl:            # DBU007: no timeout_seconds on the job or its tasks
      tasks:
        - task_key: transform
          job_cluster_key: main
          notebook_task:
            notebook_path: ../src/transform.py
```

## How to fix

Set a timeout on the job, which applies to each run, at a few times the normal duration:

```yaml
resources:
  jobs:
    nightly_etl:
      timeout_seconds: 7200
```

Or set `timeout_seconds` on every task.

## When to suppress

Suppress when runs have no predictable upper bound and something else watches them, such as an on-call alert on run duration:

```yaml
suppressions:
  - rule: DBU007
    resource: jobs.model_training
    reason: Training time varies 1-20 h; duration alert pages on-call (OPS-31)
```
