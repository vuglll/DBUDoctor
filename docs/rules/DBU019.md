# DBU019: Custom tag collides with a default tag

Severity: info. Introduced in 0.5.

A job, pipeline, cluster or SQL warehouse sets a custom tag whose key matches a Databricks default tag key, ignoring case:
- `Vendor`, `ClusterId`, `ClusterName`, `Creator`, `RunName`, `JobId`, `SqlEndpointId`;
- `DatabricksInstancePoolId`, `DatabricksInstancePoolCreatorId`.

Tags are checked in job `tags`, job and task cluster `custom_tags`, pipeline `tags` and cluster `custom_tags`, cluster `custom_tags`, and warehouse `tags.custom_tags`.

## Why it matters

Databricks applies default tags to compute, warehouses and pools. When a custom tag has the same key, "the custom tag is automatically prefixed with `x_` during propagation" and "the default Databricks tag retains its original key name" ([usage detail tags](https://docs.databricks.com/aws/en/admin/account-settings/usage-detail-tags), checked 2026-11-09). A team that tags its jobs `vendor: finance` finds `x_vendor: finance` in the cloud bill instead. Reports grouped by `vendor` see only Databricks' own value, and the job's cost goes unattributed.

The same page warns that conflicting tags set through compute policies are not renamed: the cluster or pool fails to start with an invalid settings error.

## Example

```yaml
resources:
  jobs:
    ledger:
      job_clusters:
        - job_cluster_key: main
          new_cluster:
            custom_tags:
              vendor: finance   # DBU019: billed as x_vendor
```

## How to fix

Use a key of your own, and update the cost reports that read it:

```yaml
            custom_tags:
              supplier: finance
```

## When to suppress

Suppress when cost reports already read the `x_`-prefixed key:

```yaml
suppressions:
  - rule: DBU019
    resource: jobs.ledger
    reason: FinOps dashboard groups by x_vendor (FIN-20)
```
